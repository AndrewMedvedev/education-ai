# Приглашения в организацию

В разделе текущей организации отображаются приглашения новых и существующих
пользователей. Список доступен с правом `organization-invitations.invite`,
отзыв — с `organization-invitations.delete`. Выбор ролей использует `GET /roles`
и требует права чтения ролей.

Статусы: `pending`, `accepted`, `expired`, `revoked`. Это состояния приглашения,
а не подтверждение доставки или прочтения письма. Повторная отправка доступна
для ожидающих и истёкших приглашений; для истёкшего создаётся новая ссылка.
Отзыв сохраняет запись через существующее поле `deleted_at`; миграция не нужна.
Ранее физически удалённые приглашения восстановить в истории невозможно.

## API

- `GET /api/v1/organizations/invitations?page=1&size=20` — объединённая страница
  приглашений текущей организации; ответ `Page`, без токенов приглашений.
- `DELETE /api/v1/organizations/invitations/revoke/{id}?source=iam|organization`
  — отзыв с проверкой организации и состояния приглашения.
- `POST /api/v1/organizations/invitations/{id}/resend?source=iam|organization`
  — повторная отправка. Принятые и отозванные приглашения возвращают 409.
- `GET /api/v1/invitations/preview/{token}` — email, необходимость регистрации,
  `organization_id`, `organization_name`; ответ не кешируется.
- `POST /api/v1/invitations/accept/{token}` с `{"password":"..."}` — регистрация.
  Email и организация берутся из приглашения. Подтверждение пароля проверяет UI.
- `POST /api/v1/organizations/invitations/accept/{token}` — принятие существующим
  пользователем обоих типов приглашений с проверкой email. Членство и отметка
  использования сохраняются одной локальной транзакцией. Чтение токена блокирует
  строку на время принятия/отзыва, чтобы сериализовать изменения одного приглашения.

## Проверка

Из `backend`: `uv run python tests/run_invitation_tests.py`.
Runner исключает сборку посторонних роутеров при импорте; сами модули приглашений
исполняются без подмены, репозитории в unit-тестах заменены mock-объектами.

Из `frontend`: `npm ci` и `npm run build`.

Браузерная проверка на подставном API: два поля регистрации, несовпадение паролей,
тело запроса только с паролем, переход ко входу с сохранением токена, повторная
отправка и отзыв из списка. Реальная доставка писем и интеграция с PostgreSQL
требуют запущенного окружения и этой проверкой не покрыты.
